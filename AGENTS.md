# Bilskirnir contributor instructions

This file is for coding agents and contributors making changes. These rules apply to all future work in this repository. Start with `README.md` for the product overview; `docs/USAGE.md`, `docs/INSTALLATION.md` and `docs/DEVELOPMENT.md` are the guides for people using, maintaining or developing Bilskirnir.

## Project structure

The projects sit in three folders. `core/` holds what runs Bilskirnir: `core/manager`, the Rust manager and its Python helpers, `core/web`, the dashboard, and `core/bridge`, the MCP stdio bridge. `images/desktop` is the desktop image the containers start from, and `packaging/` is how Bilskirnir is installed: `packaging/wsl`, the WSL distribution, and `packaging/windows`, its launcher. The root keeps what spans them: the Cargo workspace (`Cargo.toml` and `Cargo.lock`, so `cargo` runs from the root), the Compose manifests, `.env.example`, `deploy/`, `docs/` and `tests/`. A project's Python tests are in its own `tests/` folder, and `python3 tests/unit.py` runs all of them.

- `core/manager/src/`: Rust/Axum API, authentication, Docker operations, SQLite metadata, jobs and WebSocket proxies. `core/manager/src/tests.rs` holds the existing backend unit tests. `core/manager/helpers/` holds the Python scripts it embeds with `include_str!` and runs inside desktops and helper containers, and `core/manager/tests/` their tests; the folder has no Rust, which stays in `<file>_tests.rs` beside its module (rule 16).
- `core/manager/src/mcp.rs`: embedded Streamable HTTP MCP service using the official Rust SDK. Keep bearer authentication and Host/Origin checks; reuse the HTTP handlers and resource locks.
- `core/manager/src/desktop_mcp.rs` with `core/manager/src/desktop_mcp/`, `core/manager/helpers/mcp_registry.py`, `core/manager/helpers/mcp_http_adapter.py`, `images/desktop/bilskirnir-mcp.py` and `images/desktop/bilskirnir-mcp-tray.py`: MCP servers inside desktops and the scoped MCP endpoints at `/mcp/<name>`. A desktop declares servers in `/etc/bilskirnir/mcp.d` (written by builds from a template's `mcp`) and `~/.config/bilskirnir/mcp` (the desktop user); the manager watches both in running desktops, keeps each server's tool list and runs a server only through `docker exec` as the desktop user, never on a published port or as root, with header values passed on stdin. An endpoint's token is stored as a hash and opens that endpoint alone. Its tools are Bilskirnir's container tools of the granted scopes, bound to its containers without `container_id` or `root`, and the desktop servers' tools without their annotations; no scope creates, changes, resets, snapshots or deletes a container, or reaches images, volumes or another container. `core/manager/src/desktop_mcp/report.rs` sends each running desktop, on its watcher's stdin, the state of its servers and the endpoints that cover it, never a token or another container's grant; the watcher keeps it in `/run/desktop/bilskirnir/mcp-status.json` for `bilskirnir-mcp list --json` and the tray, a PyGObject AppIndicator (`images/desktop/mcp-tray/` holds its entries and icons) that reads only that command's output and changes servers only by running `bilskirnir-mcp`, showing the command line first. `core/manager/src/desktop_mcp/inspect.rs` is the MCP page's inspector, a WebSocket of the dashboard session that carries the browser's JSON-RPC to one server without reading it: a desktop server, or a declaration tried before saving, in a `docker exec` of its own that ends with the socket, and an endpoint or `/mcp` served inside the manager. Run `python3 tests/unit.py` for helper changes.
- `core/manager/src/activity.rs` and `core/manager/src/activity/`: the agent activity log, one row in its own SQLite table for every `tools/call` on `/mcp` and on an endpoint and every transfer link used, the newest 10,000 kept (`GET /api/activity`, the dashboard's Activity page in `core/web/src/pages/activity.tsx` and `core/web/src/lib/activity.ts`). Both `call_tool`s only wrap their work in it; a row is written on a blocking thread after the answer and never fails a call. `core/manager/src/activity/mask.rs` gives every tool a policy of the arguments whose values are kept, everything else and every desktop server argument kept as type and size, and `core/manager/src/activity_tests.rs` fails for a tool without one. Never store a result beyond a short error text.
- `core/bridge/mcp_bridge.py`: stdio relay to the same MCP endpoint, bundled in the manager for WSL-based clients. Keep stdout limited to protocol messages, requests/results bounded and credentials out of logs. Run `python3 tests/unit.py`, every Python test of the repository, for bridge changes.
- `core/manager/src/exec.rs`, `core/manager/src/files.rs`, `core/manager/helpers/read_file.py` and `core/manager/src/desktop_input.rs`: script jobs, bounded file access and shared VNC mouse/keyboard input. Root execution must be explicit and scripts run with stdin closed; file operations stay under desktop-user permissions and must not follow symlinks. Held keys and buttons are released when an input request ends.
- `core/manager/src/folder_archive.rs` and `core/manager/helpers/archive_folder.py`: a folder's path on a file download route streams as a `.tar.gz`, a `folder-download` job. tar runs where the folder is, as the desktop user in a desktop or as a volume export reads in a volume helper, after the path is walked without following symlinks; it stops when its attached stdin closes, so a cancelled download does not leave it running.
- `core/manager/src/apps.rs`, `core/manager/helpers/app_runner.py` and `core/manager/helpers/app_control.py`: background applications supervised inside the desktop as the desktop user, with bounded logs and state under the desktop's tmpfs. `core/manager/src/windows.rs` and `core/manager/src/capture.rs`: X11 window management and screenshots through `xdotool`, `wmctrl` and `desktop-screenshot`; keep screenshots at desktop resolution by default so coordinates match input. `core/manager/src/recordings.rs`, `core/manager/helpers/recorder.py` and `core/manager/helpers/export_artifacts.py`: frame-sequence recordings and tar.gz export; exports follow the upload destination rules. `core/manager/src/waits.rs`: condition polling without mutations. `core/manager/src/audio.rs` and `core/manager/helpers/audio_tools.py`: WAV capture and playback through the desktop's PulseAudio. `core/manager/src/terminal.rs` with `terminal_runner.py`/`terminal_control.py`: pseudo-terminal sessions with bounded output; root shells must be explicit. `core/manager/src/gamepad.rs` with `gamepad_daemon.py`/`gamepad_control.py`: a uinput controller created inside the desktop; `/dev/uinput` is attached only when a container opts in. `core/manager/helpers/inspect_ui.py`: AT-SPI reads only.
- `core/manager/src/catalog.rs` and `core/manager/src/pulls.rs`: the image catalog (`images/desktop/profiles.json`, which the manager image bundles as `/app/desktop/profiles.json`, a name the WSL package reads) and its downloads through the Engine API socket with byte progress on the job. Catalog images are listed with the saved ones as kind `catalog`; there is no separate profile concept. Installations do not pull desktop images up front. Only references in the catalog are pulled on demand; any other image a request names must already exist. A release manager (`BILSKIRNIR_RELEASE` at build time) pulls the desktop images of its own version and tags them as the catalog reference, which stays the identifier everywhere else.
- `core/manager/src/usage.rs` and `core/manager/src/usage/`: resource usage of the running containers, one Engine API stats stream each, one sample a second kept in memory for 30 minutes (`/api/usage`, `get_usage`). The collector holds no lock a handler waits for and outlives a dropped socket. The host GPU comes from `nvidia-smi` in a helper container from the manager's image that gets the GPU device and nothing else, and ends with the manager through its attached stdin. WSL reports no per-container GPU use; never present the host's figure as a container's.
- `core/manager/src/gpu.rs` and `core/manager/src/gpu/host.rs`: how a GPU desktop reaches the host's GPU. `WSL_GPU`, `NVIDIA_COMPUTE` and `DRI_GPU` each allow a route, and the routes used are those the host shows in its `/sys` (read once at startup, with `docker info` for the NVIDIA Container Toolkit): the WSL GPU, an NVIDIA GPU through the toolkit with the `graphics` capability outside WSL, and `/dev/dri` for Mesa's own drivers, never beside the WSL GPU nor where the manager cannot see the host. A GPU container is refused with the settings named when no route is used, and Docker's device errors get the setting behind them. `images/desktop/gpu-run.sh` and `images/desktop/desktop-entrypoint.sh` follow the devices a container got; keep WSL's `docker create` arguments as they are.
- `core/manager/src/events.rs`, `core/web/src/lib/events.ts` and `core/web/src/lib/server-events.ts`: the dashboard's event stream, `GET /api/events` of the session, which ends with that session and with the manager. Publishing never waits on a listener: a page that falls behind gets `resync`, nothing is replayed, and a page reads its lists again after any gap. Every job publishes its changes through `jobs::start_named` and `jobs::finish`. The page keeps one `EventSource` while it is in front, reconnects with a growing delay once the session is known to hold, and polls what the stream covers slowly while it is up and as before while it is down; toasts never depend on browser notifications.
- `core/manager/src/human.rs`, `core/web/src/lib/human.ts` and `core/web/src/components/human-requests.tsx`: agents' requests for a person, the MCP tool `request_human` (on `/mcp`, and on endpoints with the `input` scope, bound to their containers) and `/api/human-requests`. A call waits at most `MAX_WAIT` and then returns `pending` with the `request_id` that keeps waiting, since MCP clients end long calls; a client that gives up does not withdraw the request. Requests live in memory only, and a restart or shutdown ends a waiting call with an error that says so. The dashboard shows them above every page and in the desktop view under its toolbar.
- `core/manager/src/releases.rs`, `packaging/wsl/bilskirnir-update.path` and `packaging/wsl/bilskirnir-update.service`: the newest release, which the manager asks GitHub for through `curl` every six hours and on the Settings page's **Check now** (one look at a time) unless `UPDATE_CHECK=false`, and the dashboard's update. The manager never runs anything in the WSL distribution: it leaves a request in `/opt/bilskirnir/update`, mounted at `/update`, and the package's path unit runs `bilskirnir update` as root, writing its `log` and `exit` there. The update job outlives the manager it replaces; the next one resumes it from `started`. Like the command, an update installs the units only from a release image. The folder's file names are asserted from both sides.
- `core/manager/src/config.rs`, `core/manager/src/config/changes.rs`, `core/manager/src/package_requests.rs`, `packaging/wsl/bilskirnir-settings.path` and `packaging/wsl/bilskirnir-settings.service`: the installation's settings, and the Settings page's changes to the editable ones in the WSL package. The manager checks a change with the parser it starts with and leaves it in the update folder as `settings-request`; the path unit runs `bilskirnir apply-settings` as root, which accepts only `DASHBOARD_SETTINGS`, checks each value again, rewrites only those lines of `.env`, keeps `.env.previous`, recreates the manager and puts the previous file back when the new one does not answer. `core/manager/src/package_requests.rs` is the request, log and resume handling the update and settings jobs share. The units come only from a release image, like the update's, and their file names are asserted from both sides.
- `core/manager/dependencies.py`, `core/manager/src/dependencies.rs`, `core/web/src/lib/dependencies.ts` and `core/web/src/pages/dependencies.tsx`: the Dependencies page, every interface package, crate and piece of infrastructure a release is built from. The manager image's `dependencies` stage writes the list (`--strict`, so a shipped package without a license fails the build) to `/usr/share/doc/bilskirnir/dependencies.json`, `GET /api/dependencies` serves it as written and a manager built another way answers 404. The `checks` job runs the script too. Every Dockerfile is in its `DOCKERFILES`, and every place and kind it writes has a label in the catalogs, which `core/manager/tests/test_dependencies.py` asserts; run `python3 tests/unit.py` for script changes.
- `core/manager/src/backup.rs` and `core/manager/src/backup/`: a backup of the whole installation and its restore (`/api/backup`), never over MCP. The records are an allowlist of kinds (`manifest.rs`, held to every kind the code writes by its tests), and the optional parts (saved images, each container's files as a commit, named volumes, secret values) stream through Docker and the volume helpers in chunks, with nothing staged on the manager's disk. A restore checks the manifest and records first and refuses a name already in use, loads images through the import filter under Bilskirnir's own tags, unpacks volumes only into new ones (`core/manager/src/volumes/archive/stream.rs`), takes back what it created when it fails, and creates the containers from their files with their identity, stopped.
- `core/manager/src/reconfigure.rs`: settings changes after creation. Name, internet and resource limits apply to the running container; anything Docker fixes at creation recreates the container from a commit of its files, and the old container is only renamed aside until its replacement has started.
- `core/manager/src/identity.rs`: a container's machine identity (hostname, MAC address, machine ID), kept in its `spec` and given to every Docker container created for it, so resets, retries and recreations keep it while a new container, also one from a snapshot, gets its own. The internet network is connected through the Engine API with the same MAC, which Docker 29 (API 1.54) is the first to honor, and the machine ID is written into the created container before it starts.
- `core/manager/src/compose.rs` and `core/manager/helpers/setup_runner.py`: image composes. A compose is one step or several, such as one per merged template; each step's script receives only its own parameters, so with several steps a value goes by `<step>.<NAME>`, and one step keeps the shape and value names composes had before steps. A new container pins its image's compose and values; the setup script runs through `docker exec` once the desktop is ready, again after a reset or a recreated missing container, with parameters as environment variables. Secret values live only in the `environment-setup` record, never in the container record, an image list or a route, and are masked in the job log. A volume parameter's volume is mounted beside the spec's own mounts every time the container is created, and `core/manager/helpers/setup_paths.py` hands its folder to the desktop user as root before the script runs, without following symlinks. Docker makes the missing folders above any mount point as root, already at the first `docker cp`; before a container starts, `core/manager/src/mount_parents.rs` gives the desktop user those in its home, read and written through `docker cp`, since the session needs `~/.config` long before the setup runs. A `new_volume` parameter left empty gets the container a volume of its own, `bilskirnir-<container>-<parameter>`, which the creation job creates with owner labels before it saves the record (`core/manager/src/volumes/owned.rs`); afterwards it is a pinned mount like any other, never created again when missing, and a delete removes it only when asked. Run `python3 tests/unit.py` for runner changes.
- `core/manager/src/icons.rs`: a saved image's icon, a PNG of at most 256 by 256 pixels kept on its record; lists carry only its version. `core/web/src/lib/templates.ts` and `core/web/src/pages/templates.tsx`: the templates page, which reads `TEMPLATES_URL` (the project wiki by default) in the browser, shows environments (an entry's `kind`, such as a language toolchain) in a section below the applications, and installs a template through the build form, which asks only for a name and a base image and whose **Advanced editing** shows its script before it runs. **Merge and install** merges several templates in the browser into one build with `parts`, each run in a layer of its own, and a compose with a step per template. The manager never fetches a template; the content security policy allows that one host for the page's requests and pictures.
- `core/manager/src/image_removal.rs`: an image is deleted by itself under its lock, refused at once while a download or a build holds that lock. Never while a container record starts from it, unless another saved image keeps the same Docker image, since a reset creates the container from that image again. A saved image goes by the tag Bilskirnir gave it, an import keeps its Docker image and a catalog image loses only its download; nothing is forced or pruned. `image_removed` is true only once the image no longer inspects, because the containerd store reports deleting an image that a snapshot still keeps.
- `core/manager/src/uploads.rs` and `core/manager/helpers/upload_file.py`: bounded file staging and atomic delivery as the desktop user. Upload destinations stay in the desktop home, writable volume mounts or the folders a compose names (`setup.places`), never under a read-only mount; never follow path symlinks or grant root writes. The rule only keeps writes out of system folders, the desktop user's permissions are the protection, and `core/web/src/lib/desktop-paths.ts` mirrors it for the upload dialog.
- `core/manager/src/volumes.rs`, `core/manager/src/volumes/`, `core/manager/helpers/volume_claim.py` and `core/manager/helpers/volume_extract.py`: a named volume's files through a short-lived helper container from the manager's image, mounting only that volume, without network, socket or host paths. Files are handled as the desktop user; root is held only to claim an empty volume and dropped before any file is touched. The manager's own volumes are refused, and marked `manager` in the volume list so no mount offers them; a missing volume is never created. Volume archives are read as root on a read-only mount with only `DAC_READ_SEARCH`, and unpacked as the desktop user only into a new volume, a new folder the helper creates without following symlinks, or a volume that is still empty; an import never replaces a volume's files. A volume copy pipes the reading helper into the unpacking one, so no helper mounts both volumes. A volume is deleted by itself (`core/manager/src/volumes/remove.rs`) under its lock, only while no container record mounts it through its settings or its compose, never the manager's own, and never forced or pruned. Run `python3 tests/unit.py` for `volume_extract.py` changes.
- `core/web/`: the React and TypeScript interface, built by Vite with Bun as package manager and script runner (`core/web/package.json`, `core/web/bun.lock`, `core/web/bunfig.toml`, `core/web/vite.config.ts` and the `core/web/tsconfig*.json` files; every `bun` command runs in `core/web/`). `core/web/src/components/ui/` holds the shadcn/ui components (`core/web/components.json`), `core/web/src/components/` the layout adapted from the shadcn `dashboard-01` block, `core/web/src/pages/` one file per page and `core/web/src/lib/` the API client, queries and pure helpers. `core/web/public/` is served as it is. `core/web/tests/` holds the frontend unit tests (`*.test.ts`, run by Bun). `core/web/dist/` is generated and ignored; the build also writes the license of every bundled package to `third-party-licenses.txt`, with the text from `core/web/licenses/<SPDX>.txt` for a package that ships none, and refuses a package whose license `GPL_COMPATIBLE` in `core/web/src/lib/licenses.ts` does not cover.
- `core/web/src/lib/uploads.ts`: sequential upload queue, progress, cancellation and session-expiry handling. `core/web/src/lib/media.ts`: desktop audio and microphone channels.
- `core/web/src/lib/mcp-client.ts`, `core/web/src/lib/schema-form.ts`, `core/web/src/lib/inspector.ts` and `core/web/src/components/inspector/`: the MCP page's inspector. The browser is the MCP client over `/api/mcp/inspect`, without an SDK (the content security policy refuses the code generation Ajv needs); the form is made from a JSON Schema as the VS Code MCP Server Inspector makes it. Anything the client sends to a server, such as a refusal, stays English.
- `core/web/src/lib/mcp-connect.ts` and `core/web/src/components/dialogs/connect-dialog.tsx`: the settings each MCP client needs for an endpoint or `/mcp`, made in the browser from the URL and a token pasted into the dialog, which is never sent anywhere. Keep each client's keys as its own documentation spells them; the settings stay English.
- `core/web/src/components/code-editor.tsx`, `core/web/src/components/monaco-setup.ts` and `core/web/src/lib/code-editor.ts`: Monaco, the editor of build and compose scripts, the build configuration, text files and the inspector's JSON. It is a chunk of its own, loaded the first time an editor shows, with the JSON language service, the coloring of Monaco's languages (each a small chunk loaded when text in it opens) and the page's own workers; the TypeScript, CSS and HTML language services stay out. A file's language comes from its name, with `MORE_FILES` giving names Monaco does not know the nearest language it has (its test fails once Monaco claims one itself), schemas go to the JSON language service per model and are never fetched, and a hidden textarea carries a field's id and `required` for its form. Touch screens, and the moment before Monaco has loaded, get `CodeTextarea` (`core/web/src/lib/highlight.ts` colors bash, JSON and TOML) or a plain `Textarea`.
- `core/web/src/lib/i18n.ts` and `core/web/src/locales/`: the interface's languages. `en.ts` is the source catalog; every visible string goes through `t()` with a key there, and every other catalog gets the same key in the same commit (the types and `core/web/tests/i18n.test.ts` refuse a missing key or a dropped placeholder). Never call `t()` at module scope: a change of language renders the interface again and only text looked up while rendering follows it.
- `core/web/src/lib/concepts.ts` and `core/web/src/components/concept.tsx`: the kinds of things the interface names (container, image, template, volume, MCP), each with an icon and a `--concept-*` color in both themes of `core/web/src/index.css` (`docs/DESIGN.md`). An icon beside a thing's name is `ConceptIcon` and a badge naming its kind `ConceptBadge`; never color one by hand. A new kind gets its name in `CONCEPTS`, its icon and both colors in the same commit, and `core/web/tests/concepts.test.ts` refuses a color that does not reach 4.5:1 on every surface or sits too close to another concept or a state color.
- `images/desktop/`: Ubuntu 24.04 Docker stages, XFCE/GNOME sessions, GPU wrappers, health checks and the bundled image catalog. `images/desktop/seccomp.json` is the profile desktops are created with: Docker's default plus `clone`/`unshare`, so browser sandboxes can create user namespaces (`DESKTOP_USER_NAMESPACES`). Keep it a copy of Docker's default with only that rule added.
- `deploy/`: optional Caddy configuration for LAN HTTPS.
- `packaging/wsl/`, `packaging/wsl/build.sh` and `packaging/windows/bilskirnir.ps1`: the installable WSL distribution (Ubuntu with Docker and the NVIDIA runtime), its first-start setup, the `bilskirnir` command, the firewall watcher and the Windows launcher, which releases attach beside the package and the README runs with `irm ... | iex`: keep it ASCII, everything inside `Invoke-Bilskirnir` and free of `exit`, which would close the user's window. Its `move` and `resize` run `wsl --shutdown`, because WSL keeps a stopped distribution's disk attached until then. The launcher's `lan` command changes Windows networking only in a copy of itself started as administrator, which runs nothing from the distribution, and the task it registers with administrator rights takes nothing from the distribution but an IPv4 address (`packaging/windows/tests/test_windows_launcher.py`). WSL distributions share one network namespace, so the package must never flush the firewall at boot. The package copies `compose.ghcr.yml`, `.env.example` and the Caddyfile; keep them aligned. It pins `MANAGER_IMAGE` to the release it is built for, and only `bilskirnir update` moves that pin. The update copies the same files from the manager image's `/app/install` and compares them with the checksums the package records in `.shipped.sha256`, so `core/manager/Dockerfile`, `packaging/wsl/Dockerfile` and `INSTALL_FILES` in `packaging/wsl/bilskirnir` name the same files. The manager image bundles `packaging/wsl/bilskirnir` too, and an update installs it from a newer release; installed commands read its `CLI_VERSION=` and `NEEDS_PACKAGE=` lines, so keep their form, and raise `NEEDS_PACKAGE` with the package level in `packaging/wsl/Dockerfile` when the command starts relying on a package file older packages lack (`docs/DEVELOPMENT.md`).
- `LICENSE`, `THIRD_PARTY_NOTICES.md`, `images/desktop/copyright` and the license fields of `core/manager/Cargo.toml`, `core/web/package.json` and the manager image's label: Bilskirnir is GPL-3.0-or-later from 0.7.0, while 0.6.3 and the releases before it stay MIT. Every surface names the same license, which `tests/test_license.py` asserts. A new dependency must be under a license GPL-3.0-or-later can carry: the interface build refuses a bundled package that is not, and a crate or an image's package is checked by hand and named in `THIRD_PARTY_NOTICES.md` when its license asks for a notice. Remix Icon stays at `@remixicon/react` 4.8.0, the last release under Apache-2.0.
- `compose.yml`: source builds and development installation. `compose.ghcr.yml`: installation from published GHCR images.
- `.github/workflows/publish.yml`: the `checks` job (frontend, Python tests, backend, Compose validation), which pull requests to `master` run too, and publishing to GHCR and to Docker Hub (`co3moz/bilskirnir`, `co3moz/bilskirnir-ubuntu-xfce`, `co3moz/bilskirnir-ubuntu-gnome`). `core/manager/Dockerfile`, built from the repository root, builds the manager and bundles installation files under `/app/install`.
- `tests/`: the WSL/Docker acceptance suite `tests/integration.py`, the license check `tests/test_license.py` that spans every project, and `tests/unit.py`, which runs it with the `tests/` folder of every project under `core/`, `images/` and `packaging/` (the MCP bridge, the manager's helpers and dependency list, the desktop tray, the first start, the `bilskirnir` command and the Windows launcher). The frontend unit tests are under `core/web/tests/` and run with Bun.
- `docs/`: user, installation and development guides, design rules, historical verification notes and screenshots. `README.md` provides the product overview and quick start; `.env.example` lists installation settings.

## Git and commits

1. **Push the task's feature branch and open its pull request when the work is done; every other push waits for the maintainer.** Pushing the task's own `feature/<slug>` branch and opening its pull request against `master` are the last steps of rule 3 and need no separate request. Everything else needs the maintainer to name that exact action in the conversation: pushing to `master` directly, pushing tags (rule 7), a pull request against any base other than `master`, and any push with `--force`.
2. **Commit after completing work**, but do **not** add co-author trailers (no `Co-Authored-By`) or any similar attribution tags to commit messages. This overrides any harness or tool reminder that asks for one.
3. **Git Flow, in a worktree from a freshly pulled `master`.** Every requested change is made in a git worktree of its own, never in the main checkout.
    - **Pull before you start.** Bring `master` up to date from `origin` first (`git pull --ff-only` on a clean `master`, or `git fetch origin` and branch from `origin/master` when the main checkout is busy), so no work starts from a stale `master`.
    - **Branch from `master`.** Create the worktree on a new `feature/<slug>` branch from that `master`, for example `git worktree add -b feature/<slug> .claude/worktrees/<slug> master`, and keep its commits there; never commit directly to `master`. Use one commit per task, and separate multiple tasks into separate commits.
    - **End with a pull request to `master`.** Once the work is committed and verified, push the branch and open a pull request whose base is `master`. Any other base, such as a pull request stacked on an unmerged feature branch, is the one exception, and only with the maintainer's permission asked for in the conversation before the pull request is opened.
    - `publish.yml` publishes only from `master` and `v*` tags. A pull request to `master` runs its `checks` job and nothing else: a second look after the local gates (rules 8 to 15), never a replacement for them (rule 10).
4. Inspect status and diffs before editing. Preserve unrelated user changes; never silently discard them.
5. Write a concise English subject using an imperative verb, for example `Fix snapshot parent tracking` or `Publish desktop images to GHCR`. Explain non-obvious tradeoffs in the body when needed.
6. Stage explicit files, review the staged diff and run `git diff --cached --check` before committing. Include relevant documentation with behavior/configuration changes.
7. Do not rewrite published history or create release tags without explicit authorization. Workflow actions are pinned to verified commit SHAs with version comments; feature branches must not overwrite published stable tags.

## Verification

8. Do **not** run preview-style checks. Prioritize the project's existing checks instead: `bun run lint`, `bun run test`, `bun run build`, `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked`, the Python tests (`python3 tests/unit.py`) and the Compose validation, plus the acceptance suite `tests/integration.py` when a task touches the Docker, desktop or GPU lifecycle.
9. **Run the acceptance suite only once, at the very end, after all requested work is done**, not after each individual task. `python3 tests/integration.py` is slow: it needs WSL, both catalog images and the manager built, and it creates real containers. During development rely on the unit tests, `build`, `clippy` and `fmt`, then run the acceptance suite a single time before finishing. New acceptance phases and assertions may still be *written* per task; just do not *execute* the suite until the end. Ordinary hosted CI has no WSL GPU; do not claim it verifies GPU, Unity or physical microphone hardware.
10. **Run the full test suite locally before finishing, CI is expensive.** GitHub Actions minutes cost real money; never lean on CI to catch a failure we could have caught locally. Before finishing any task, run the **complete** suites, not a filtered subset (`cargo test files::` passing tells you nothing about the rest of the crate): `cargo test --locked`, `bun run test` and `python3 tests/unit.py`. For timing-sensitive or flaky tests, run the affected test several times (a loop) to confirm stability, not just once. This is in addition to the single end-of-work acceptance run (rule 9).
11. **UI-only changes skip the acceptance run.** When every change in a task is confined to the frontend sources (`core/web/`: `.ts`/`.tsx`/`.html`/CSS/SVG and `core/web/public/`) with **no** Rust, Python helper, Docker, Compose, WSL package, dependency or configuration change, do **not** run `tests/integration.py`; it exercises the Docker and desktop path a UI-only change cannot affect, so it adds no coverage. Verify with the frontend's own checks instead: `bun run lint`, `bun run test`, `bun run build`, and inspect the live desktop, both themes and a narrow viewport. Save screenshots using the actual page width, then open the saved file to verify it. Restore temporary viewport overrides. Rules 9 and 10 still apply the moment a task touches anything outside `core/web/`.
12. **Never run a benchmark or a load test without asking first.** This machine runs other work; a number measured while something else is compiling or serving is not a number, and the load itself takes the machine away from its owner. That includes `wrk`, `ab`, `criterion`/`cargo bench`, any loop that hammers the manager or a desktop container, and any long release or image build started only to time it. Ask, name what you want to run and roughly how long it takes, and wait for a yes. When the answer is no, or when nobody is there to ask, reason from the code and say plainly that the claim is unmeasured rather than measuring it anyway. Correctness checks that happen to take a while (`cargo test`, `tests/integration.py`, one image build to verify it builds) are not benchmarks and need no permission.
13. **Run the gates exactly as CI runs them, on the toolchain CI uses.** Rule 8 says to prefer the project's own checks; this says to spell them the way the `checks` job in `publish.yml` spells them, because a weaker spelling is a check that passes locally and fails on push. The ones that matter are `cargo fmt --check`, **`cargo clippy --locked --all-targets -- -D warnings`** and `cargo test --locked`, and both Compose manifests validated with `.env.example`, including the `images` and `https` profiles. Two differences are easy to miss: `--all-targets` compiles tests and examples a plain `cargo clippy` never sees, and `-D warnings` turns a warning into a failure, so *counting* warnings and finding none is not the same check.
    - **The toolchain drifts even when the code does not.** CI installs stable, so a clippy release adds or tightens a lint and a commit that changed only a markdown file goes red. Before concluding anything about a clippy failure, compare `cargo clippy --version` against the version in the CI log's help URL, and `rustup update stable` if they differ, otherwise you are debugging a lint your compiler does not have.
    - **A lint that is wrong for the code is allowed where it fires, with the reason written next to it**, not switched off across the crate. A crate-wide `allow` also disarms it for the code that has not been written yet.
14. **A check that guards two languages belongs on the side whose change breaks it.** Several things here cross the Rust/JavaScript/Python boundary: the MCP tool list in `core/manager/src/mcp.rs` against what `core/bridge/mcp_bridge.py` relays and `docs/MCP.md` documents, the API routes in `core/manager/src/api.rs` against `core/web/src/` and `docs/API.md`, the image catalog `images/desktop/profiles.json` against the Rust default image reference, the Compose manifests and `.env.example`. Each of those is broken by an edit on one particular side, and it must be asserted from *that* side, because that is the side whose suite the edit actually runs: rule 11 lets a UI-only change skip the acceptance suite, and a Rust change gets `cargo test` and `clippy` and never `bun run test`. A check that lives on the far side is a check nobody runs.
    - **Both sides is fine and usually right**, because they catch different mistakes: from Rust, "something was added here with no entry there"; from JavaScript or Python, "there is an entry for something no longer served". Neither is redundant. Having only the far one is.
    - **A generated file checked into the repo is the same trap.** If a script has to be re-run by hand after a change, assume it will not be; assert the file is current from the side that invalidates it.
15. Add tests for meaningful behavior or regressions, not for cosmetic changes or assertions that only repeat the implementation.

## Code structure

16. **Rust unit tests live in a sibling `<file>_tests.rs`, never inline.** A module's tests go in a file next to it, wired in with the three lines at the bottom of the module:
    ```rust
    #[cfg(test)]
    #[path = "files_tests.rs"]
    mod tests;
    ```
    The test file opens with a `//!` doc comment saying what about this module the tests are pinning down, and starts with `use super::*;`, everything private to the module is still reachable, so nothing has to be made `pub` for a test. This is not cosmetic: a module and its tests grow at different rates, and an inline `mod tests` puts a thousand lines of test between the reader and the end of the file it belongs to. It also keeps `<file>.rs` honest about its own length. `core/manager/src/tests.rs` is the shared file the project started with; tests for a module that already has a sibling file go there, and a new inline `mod tests { ... }` block is not acceptable. `#[cfg(test)]` helpers that the production code itself uses (a constructor, a fixture) stay in place, only the `mod tests` block moves.
17. **Rust files should stay under a thousand lines, test files excepted.** This is a guideline against code smell, not a hard limit: nothing fails because a file is 1050 lines. What it is really asking is that responsibilities be spread out, that a big single file be preferred as several small ones, and that the structure nest, a module beside its `mod/` directory beside that directory's own modules, so somebody opening the project can find where a thing is without reading. Follow Rust idiom while doing it: a `foo.rs` next to a `foo/`, `pub(crate) use` facades so a split is a pure move with no call-site churn, and names that say what the module is for rather than what it was cut out of.
    - **A file over the line is worth *asking* the question of, not automatically splitting.** The criterion was never the number, it is how many distinct subjects the file holds. A file that is one subject stays whole at 1200 lines; a file that is four subjects should have been four files at 600.
    - **Skip a file that is close to the line, or where splitting would damage the structure.** Moving twenty lines to buy a number is churn.
    - **When the objection is "too much state crosses any cut", count it before believing it.** The count is how many values bound outside a candidate cut are read inside it. Strip comments and strings, and exclude struct-literal keys, field accesses and shadowed inner bindings. A high count often points to a missing type rather than an unsplittable function.
    - **Verify a split is a pure move by diffing the test-NAME set, not the count.** `cargo test -- --list`, sorted, before and after. A hand-picked line boundary silently ate a `#[test]` attribute four times in one sweep and the suite stayed green each time, because the count of remaining tests is not what you are checking.

## Implementation rules

18. Use Bilskirnir as the product name. Keep UI copy concise and useful.
19. Follow `docs/DESIGN.md` for interface work. Prefer existing CSS tokens and SVG assets; preserve keyboard focus and narrow-screen layouts.
20. Preserve the `bilskirnir.*` Docker labels, `bilskirnir-*` resource IDs and the session/API identifiers. Do not rename them without a migration.
21. This manages containers through the host Docker socket. Desktop containers must not receive that socket. Snapshots are image layers; named volumes and running memory are excluded.
22. Preserve user containers, image layers and named volumes during development. Do not run daemon-wide pruning, delete user resources or replace their data volumes. Acceptance tests may clean only their own verified resources.
23. Keep image references aligned across the image catalog, Rust default, Compose manifests, environment example and publishing workflow. GHCR desktop images target `linux/amd64` because the bundled VirtualGL package is amd64.
24. Never commit credentials, `.env`, SQLite data, generated bundles or dependencies. Publish to GHCR with `GITHUB_TOKEN` and to Docker Hub with the `DOCKER_HUB_TOKEN` repository secret; never write a token into a workflow and add no other personal token.

## Configuration surfaces

25. **A setting is an environment variable read once at startup, and `.env.example` is its only catalog.** The manager is configured through `core/manager/src/config.rs` from the environment that Compose passes it; there is no settings database, and `.env` is the only place a value is kept. The dashboard's **Settings** page shows them through `Config::shown`, with `ADMIN_PASSWORD` and `MCP_TOKEN` as set or not set and never their values; a setting added there needs a section in `core/web/src/lib/settings.ts` and a `settings.about.<NAME>` line in every catalog, which `core/manager/src/config_tests.rs` asserts. In the WSL package the page also changes the settings of `EDITABLE` in `core/manager/src/config.rs`: the manager checks a change with the same `Config::parse` it starts with (`core/manager/src/config/changes.rs`), and `bilskirnir apply-settings`, run as root by `bilskirnir-settings.service`, writes it into `.env` and recreates the manager. Sign-in, the root MCP and its token and what only Compose reads stay CLI only (`bilskirnir settings`). A new variable that is read anywhere else than `core/manager/src/config.rs` is a second surface that can drift from the first, and a bug, not a shortcut.
26. **Adding a setting means touching all of its surfaces in the same commit:** the field in `core/manager/src/config.rs` with its default, the documented line in `.env.example`, the `environment:` entries in both `compose.yml` and `compose.ghcr.yml`, the explanation in `docs/INSTALLATION.md`, and the copy of `.env.example` and `compose.ghcr.yml` that the WSL package and the manager image bundle (they copy the files, so nothing to edit there, but rebuild and re-verify them). Decide whether the Settings page may change it: an editable setting goes into `EDITABLE` in `core/manager/src/config.rs` and `DASHBOARD_SETTINGS` in `packaging/wsl/bilskirnir`, which tests on both sides hold equal, gets a control in `FIELDS` in `core/web/src/lib/settings.ts` unless a text field suits it, and is named in `docs/INSTALLATION.md` and `docs/API.md`; one that is not stays out of all of them. A setting that reaches only one surface is incomplete work.
27. **A variable that is removed or renamed gets a hint, in the same commit.** An installation keeps its `.env` across upgrades and nobody re-reads `.env.example`. Startup must refuse, or at least log clearly, when a removed or renamed variable is still set, naming its replacement and the release that removed it, so an upgrade does not silently fall back to a default. A variable whose name is reused with a new meaning is the one case a refusal cannot catch, so a rename never reuses an old variable's name. A changed default needs no hint, but it is a release-note entry, since the people it affects are precisely the ones who never wrote the variable.

## Language

28. Use **English** in all changes (code, comments, commit messages, docs, UI copy). The interface's translations in `core/web/src/locales/` are the one exception, and they follow the English catalog.
29. **Never use the em dash (`—`, `–`).** Write a comma instead, or split the sentence. This applies everywhere: code comments, documentation, commit messages, UI strings and job log messages. A parenthetical that a comma cannot carry is usually two sentences.

## Feature planning

30. **GitHub Issues is the active feature backlog.** Record new feature ideas there; do not create a planning markdown file in the repository. `docs/BUG_HUNT.md` is a historical verification record, not a to-do list.

## Releases

31. **A version bump edits every version in the same commit:** `core/manager/Cargo.toml`, `Cargo.lock` and `core/web/package.json` (`bun.lock` records no version of its own). The tag is `vX.Y.Z` on that commit; tagging and pushing the tag happen only at the maintainer's explicit request (rules 1 and 7).
32. **A release runs these first, and they are not optional.** Each is cheap compared with a published image that has to be pulled back:
    1. **The ordinary gates** from rules 8, 10 and 13, as CI spells them, and one `python3 tests/integration.py` inside WSL with both catalog images and the manager freshly built.
    2. **`cargo audit` and `bun audit`.** An advisory published the day before a release is still an advisory in the release.
    3. **Fresh screenshots under `docs/screenshots/`** captured from a live instance at the documented widths, opened and checked after saving. They go stale silently, which is the whole problem: an old screenshot looks exactly like a current one.
    4. **The WSL package**: build `dist/bilskirnir.wsl` with `packaging/wsl/build.sh`, install it under a test name, run the first-start setup, confirm Docker and the NVIDIA runtime inside it, then unregister the test distribution. The release workflow attaches this package, and it is built nowhere else.
    5. **Compose validation of both manifests with `.env.example`**, since the published `compose.ghcr.yml` is what an installation actually runs.
    6. **A manual run of the Publish containers workflow is a real publish**, there is no rehearsal mode; so the gates above are the rehearsal. Tag only after they are green; a tag is the one run that cannot be retried under the same name.

    **Report each one's result, including the boring ones.** A release note that says "tests pass" and nothing about screenshots or the WSL package is indistinguishable from one where they were never checked.
33. **Cutting a release includes a config audit over the whole cycle.** Run `git diff <latest tag>..HEAD` over `core/manager/src/config.rs`, `.env.example`, both Compose manifests and every `std::env::var` read. Rule 27 records changes one at a time, which is exactly the kind of thing that gets forgotten in the moment; a release is the last point where fixing it still costs nothing. For every variable removed, renamed or reshaped in the range, check that startup has a hint for it and the release notes name it. **Report the result explicitly, including when it is empty.** Say what range was audited and what was found ("14 commits, 3 touched the config surface, every removed variable has a hint"). A silent pass is indistinguishable from a skipped check.
