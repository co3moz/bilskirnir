# Developing Bilskirnir

[Back to the README](../README.md)

Bilskirnir has a Rust/Axum backend and a React and TypeScript frontend built with Vite, Tailwind CSS and shadcn/ui components, with [Bun](https://bun.sh) as its package manager and script runner. The manager uses the Docker CLI through the host Engine socket. Desktop images contain Ubuntu, the desktop session, VNC and the graphics helpers.

Read [AGENTS.md](../AGENTS.md) for implementation constraints and commit rules before changing the project.

## Build and run from source

In a checkout inside WSL, copy the example settings and set `ADMIN_PASSWORD`, or use `AUTH_MODE=none` for a private local development instance:

```bash
cp .env.example .env
docker compose --profile images build desktop desktop-gnome manager
docker compose up -d --no-build manager
```

This builds both catalog images and the manager. The manager is tagged `bilskirnir/manager:local`. Desktop builds use the GHCR references in the image catalog, so local builds and registry installations agree on image names.

When a catalog image is missing, its row under **Images** offers a download button, which pulls the published image, and a build button, which builds it from the manager's bundled Docker context. Creating a container or an image from a missing catalog image downloads it in that job. Pulls use the Engine API socket so the job can report byte progress; the socket follows `DOCKER_HOST`, and a daemon that is not on a Unix socket is pulled through `docker pull` without byte counts. Script builds, snapshots and imported images follow the catalog images in the same list.

## Work on the interface

The Vite project lives in `web/`: `web/index.html`, the React sources under `web/src` and static files under `web/public`, which are served as they are. `vite.config.ts`, the TypeScript projects and `package.json` sit at the repository root. Pages live in the URL fragment (`#/images`, `#/desktop/<id>`), so the manager serves one `index.html` for all of them. Vite names the files under `web/dist/assets/` after their content, and the manager lets browsers keep those for a year; `index.html` and the other files are revalidated on every load, so an upgraded manager never serves a page that points at assets it no longer has.

The layout follows the shadcn `dashboard-01` block: an inset sidebar, a site header, summary cards, an interactive chart and data tables with a detail drawer. Add a shadcn component with `bunx shadcn@latest add <component>`; it reads `components.json` and writes to `web/src/components/ui/`, which is project code from then on. The CLI also tends to add the `shadcn` package, an `@import "shadcn/tailwind.css"` line and `web/src/lib/utils.ts`; drop them, since that stylesheet is vendored as `web/src/shadcn.css` and components import `cn` from the `cn` package. See [DESIGN.md](DESIGN.md) before changing colors or layout.

To work on the interface with hot reload, start a manager (for example with Compose, as above), then run the Vite server, which proxies `/api` including the WebSockets:

```bash
bun install
bun run dev
```

Open `http://localhost:5173`. Set `BILSKIRNIR_URL` when the manager does not listen on `http://127.0.0.1:8080`.

### Translate the interface

Every visible string in `web/src` goes through `t()` from `web/src/lib/i18n.ts` with a key from `web/src/locales/en.ts`, the English catalog that the other languages follow: `de.ts`, `fr.ts`, `es.ts` and `tr.ts`. A key names where its text appears, `{name}` marks a value the code fills in, and a pair of keys ending in `.one` and `.other` holds the plural forms that `plural()` picks with the language's own rules. `rich()` fills placeholders with elements, such as a path in `<code>`, so each language keeps its own word order around them. Dates, numbers and lists follow the language through `formatDate`, `formatNumber` and `formatList`.

To add or change text, edit `en.ts` and give every other catalog the same key in the same change. The catalogs are typed against `en.ts`, so a missing or misspelled key fails `bun run build`, and `tests/i18n.test.ts` fails when a translation drops a placeholder, a plural form is missing its pair or a message uses a long dash. Call `t()` while rendering or handling an event, never at module scope: a change of language renders the interface again, which only reaches text looked up then.

The language is the browser's first one that has a catalog, English otherwise, until someone picks one in the account menu or on the sign-in page; that choice is kept in `localStorage`. To add a language, add its catalog, register it in `catalogs`, `localeNames` and `regions` in `i18n.ts`, and the tests check it like the others. Text that the manager returns, such as API errors and job logs, stays English.

## How the containers connect

The manager and desktop containers run on the same WSL Docker Engine. Only the manager receives `/var/run/docker.sock`.

Containers are created with `--security-opt seccomp=desktop/seccomp.json` unless `DESKTOP_USER_NAMESPACES=false`. The file is Docker's default profile from `github.com/moby/profiles/seccomp` v0.2.4, the version Docker Engine 29.9 vendors, with one rule appended that allows `clone` and `unshare`, so browser and Electron sandboxes can create user namespaces. To follow a newer Docker release, copy its `vendor/github.com/moby/profiles/seccomp/default.json` and append that rule again; the Rust tests check that the rule is present and that calls Docker reserves for `CAP_SYS_ADMIN` stay refused. Docker fixes the profile when it creates a container, so existing containers pick up a change only when they are recreated.

The MCP server is mounted on the same Axum router at `/mcp`. Its bearer authentication is independent of browser sessions, but the outer Host policy and matching-Origin checks still apply. Tool calls reuse HTTP handlers and resource locks; do not implement separate Docker mutations for MCP. Mouse and keyboard control use shared RFB 3.8 connections and Fence acknowledgement; keys and buttons held within a request are released when it ends, and relative movement is emulated from the position reported by `xdotool`. Scripts run from an unlinked temporary file with stdin closed. Background applications are supervised by `app_runner.py` inside the desktop, which keeps a bounded log under `/tmp`; `app_control.py` reports, reads and stops them. Window tools use `xdotool` and `wmctrl`, and `desktop-screenshot` accepts a maximum width, a region and a window ID. Accessibility inspection uses `python3-pyatspi` and the session's AT-SPI bus. Terminals run bash on a pseudo-terminal supervised by `terminal_runner.py`. Containers created with `gamepad=true` get `/dev/uinput` and a device cgroup rule for input devices; `gamepad_daemon.py` runs as root inside the desktop only, creates the virtual controller and its `/dev/input` nodes, and never touches the host.

Each container has a private internal bridge to the manager. Browser desktop and media connections pass through the manager; VNC ports are not published on the host. A second bridge provides internet egress and is attached or detached by the container's internet setting.

Audio uses authenticated WebSockets carrying 48 kHz float32 PCM: stereo output at roughly 384 KB/s and mono microphone input at roughly 192 KB/s. The browser needs a secure context for microphone permission, so LAN microphone access uses HTTPS.

The database records immutable image IDs so later tag changes do not change an existing container's base. Operations on the same container are serialized, while unrelated containers and image builds can proceed independently.

Standard Docker CLI operations have a 120-second timeout; image builds and commits have a one-hour timeout. Job logs retain their last 256 KiB, and the job list returns the latest 100 entries without loading their full logs.

Uploads stream through bounded staging before delivery as UID/GID 1001:1001. Destinations must remain within the desktop home, writable mounted volumes or the folders the container's compose names, and never under a read-only mount; `web/src/lib/desktop-paths.ts` mirrors that rule for the upload dialog. The receiver rejects symlink traversal and writes completed files atomically. Preserve these constraints when changing the upload path.

A volume's files are reached through a helper container started from the manager's own image with the volume at `/volume`, the same Python helpers as a running desktop, `--network none`, `--read-only`, `--cap-drop ALL` and `no-new-privileges`. Reads run as 1001:1001 on a read-only mount. Writes start as root with only `CHOWN`, `SETUID` and `SETGID` so `volume_claim.py` can give an empty, root-owned volume to the desktop user, then switch to 1001:1001 before running anything. A volume archive is written by tar as root on a read-only mount with only `DAC_READ_SEARCH` added, and an import creates a new volume and unpacks into it as 1001:1001 after the manager has gunzipped the upload against `IMAGE_ARCHIVE_MAX_MB`. Keep the Docker socket and host paths out of the helper, and keep the manager's own volumes refused.

## Add a catalog image

Add an entry to `desktop/profiles.json` with an ID, display name, image reference, session, description, `build_target` and `build_service`; every field is required. The file keeps its name because the WSL package's `bilskirnir update` reads it from the manager. Then add the matching Dockerfile stage, startup session and desktop metadata labels; the `bilskirnir.profile` label carries the catalog ID.

Update Compose and the publishing workflow if the new image needs its own build service or published image. Rebuild the manager so its catalog includes the image. Keep image references aligned across the catalog, configuration defaults and installation files.

## Add a template

The **Templates** page lists templates from the project's GitHub wiki. The wiki is a git repository of its own, `https://github.com/co3moz/bilskirnir.wiki.git`, editable by the repository's collaborators. The page reads three kinds of files from its `templates/` folder through `raw.githubusercontent.com/wiki/co3moz/bilskirnir/`:

```
templates/index.json   the list
templates/<id>.json    a template: a build configuration
templates/<id>.png     its icon, at most 256 by 256 pixels
```

`index.json` names each template once:

```json
{
  "templates": [
    {
      "id": "unity",
      "name": "Unity Hub",
      "description": "Unity Hub with a volume for editor installs.",
      "tags": ["games", "3d"],
      "requires": "0.5.0"
    }
  ]
}
```

`id` is lowercase letters, digits and dashes, up to 64, and names the two files. `name` is 1 to 100 characters, `description` at most 500 and `tags` at most eight short texts. `requires` is the oldest release that can build the template: set it when the template uses something newer than an installed release understands, such as a new compose parameter type, since that release would refuse the build. A release older than `requires` shows the template without **Install**.

To make a template, build the image in the dashboard with **Build image**, give it its compose, description and icon, create a container from it and check that the setup works. Then **Export configuration** copies exactly the JSON `<id>.json` holds. Its `icon` line can be dropped, since the page takes the icon from `<id>.png`; the line is used only when that file is missing. Save the icon at 256 by 256 pixels.

An image can bring [MCP servers that run inside its desktops](MCP.md#mcp-servers-inside-a-desktop), such as a browser automation server attached to its Chrome. The build request declares them in `mcp`, which **Export configuration** includes, and the build writes each as `/etc/bilskirnir/mcp.d/NAME.json` in the image, so every container created from it, and from its snapshots, has them. Each entry is the file's content with its `name`, a stdio command or a loopback URL, as the MCP guide describes; at most 16, each name once. A `${NAME}` in its arguments, variables, URL or headers is filled in from the container's compose values when the manager starts the server, so the template can let the user choose what the server gets:

```json
{
  "name": "Chrome with Playwright MCP",
  "base_image": "ghcr.io/co3moz/bilskirnir/ubuntu-xfce:24.04",
  "script": "#!/usr/bin/env bash\n...",
  "compose": {"parameters": [{"name": "CAPS", "type": "text", "label": "Extra tool groups", "default": "network,storage"}]},
  "mcp": [
    {
      "name": "playwright",
      "description": "Playwright MCP attached to the agent's Chrome",
      "command": "chrome-mcp",
      "args": ["mcp"],
      "env": {"CHROME_MCP_CAPS": "${CAPS}"}
    }
  ]
}
```

The script installs the program the command names; the manager runs it as the desktop user only when an endpoint needs its tools, never on a port. **Install** shows the declarations under the script, where the user can leave one out before building. To say on the card which servers a template provides, list their names in its `index.json` entry, as `"mcp": ["playwright"]`.

```bash
git clone https://github.com/co3moz/bilskirnir.wiki.git
cd bilskirnir.wiki
mkdir -p templates
# Add templates/<id>.json and templates/<id>.png, and the entry in templates/index.json.
git add templates
git commit -m "Add the Unity template"
git push
```

The wiki has no review or checks before a push reaches every installation, which reads the list within about five minutes. Open **Templates** after pushing: an entry the page cannot offer is listed under the cards with the reason, and **Install** reports a template file that does not fill the build form. Every installation's browser fetches these files, and a template's script runs as root in the build, so treat a change to the wiki as a release. The first page of the wiki has to be created on GitHub before the repository can be cloned.

**Merge and install** builds a template together with others, so write every template to work beside them. A merged build runs each template's build script in a layer of its own, in the order the user chose, and each compose as a step whose script receives only its own parameters; [the API guide](API.md#merged-templates) has the details. That leaves the files the scripts share:

- Start from `apt-get update` and end with `rm -rf /var/lib/apt/lists/*`, since another template may have cleaned up before yours runs.
- Change shared files by adding to them, and check before adding, so a second run or another template's copy of the same software finds them as it expects. Never remove or replace what another template may have put there.
- Give a panel launcher its own plugin id: the `vscode` template takes `plugin-23`, so a new one takes the next free number rather than reusing one a template already checks for.
- Keep the template's compose volume paths its own, such as `/home/desktop/workspace` only for the template that owns that workspace: two steps cannot mount volumes at one path.
- Name the template's base image as the others do. A merge builds on the first template's base and warns about any other.
- Give the template's MCP servers names of their own, such as `playwright` rather than `mcp`: a merged image has one `mcp.d` folder, so a merge of two templates that declare a server under the same name is refused, and the build refuses a duplicate name too.

A template exported from a merged image has `parts` and `template_ids`, and can be listed like any other; choosing it together with one of the templates it holds is refused.

## Check a change

For the frontend, with Bun 1.4 or later:

```bash
bun install --frozen-lockfile
bun run lint
bun run test
bun run build
```

`lint` runs ESLint and checks Prettier formatting (`bun run format` fixes it), `test` type-checks and runs the unit tests in `tests/*.test.ts` with Bun's test runner, and `build` type-checks the application and writes `web/dist/`.

For the backend:

```bash
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

Check the bundled stdio bridge with Python's standard library test runner:

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
```

Validate both installation manifests:

```bash
docker compose --env-file .env.example --profile images config --quiet
docker compose -f compose.ghcr.yml --env-file .env.example --profile https config --quiet
```

For Docker or GPU lifecycle changes, build both catalog images and the manager, then run the acceptance suite inside WSL:

```bash
python3 tests/integration.py
```

The suite creates uniquely named resources and cleans only resources it owns. It covers both catalog images, hardware OpenGL, authentication, VNC and screenshot output, audio channels, uploads, image builds, snapshots, volumes, network changes, concurrent operations and recovery, plus the agent tools: background applications, windows, held input, relative pointer movement, waits, diagnostics, recordings and MJPEG video, artifact export, file tools, downloads, audio capture and injection, terminals, accessibility inspection, the virtual gamepad and container reset. It does not launch Unity or test a physical microphone.

Inspect interface changes in a live browser at desktop and narrow widths. Open saved screenshots to confirm their actual layout before adding them to the documentation. Do not run acceptance tests or rebuild images for a wording-only change.

## Publish container images

The **Publish containers** workflow checks frontend and backend code and validates Compose before publishing three `linux/amd64` images:

| Image | Moving tags from `master` |
| --- | --- |
| `ghcr.io/co3moz/bilskirnir` | `latest` |
| `ghcr.io/co3moz/bilskirnir/ubuntu-xfce` | `24.04`, `latest` |
| `ghcr.io/co3moz/bilskirnir/ubuntu-gnome` | `24.04`, `latest` |

Every publication also gets a `sha-<full-commit>` tag. A release tag such as `v1.2.3` publishes `1.2.3` and `1.2` for all three images without moving the `master` tags. Its manager is built with `BILSKIRNIR_RELEASE=1.2.3`: it downloads the `1.2.3` desktop images and tags them as their catalog references, and carries the version in its `bilskirnir.release` label, which `bilskirnir update` reads. Other builds leave it empty and download the catalog references. Publishing is allowed from `master` or `v*` tags; manual runs follow the same restriction. A pull request to `master` runs only the checks, and a newer commit on it cancels the run of the older one. Documentation-only changes trigger neither image builds nor pull request checks.

The workflow uses `GITHUB_TOKEN` with package write access, BuildKit caches in the GitHub Actions cache and actions pinned to commit SHAs. It reads each published manifest back by digest to check registry access. The two desktop images build one after the other on the same builder, so they publish the same layers for the `common` stage of `desktop/Dockerfile` and a host downloads and stores that part once; the job fails when those layers differ. The `checks` job keeps its compiled Rust dependencies with `Swatinem/rust-cache`, saved only from `master` and read by tags and pull requests. Hosted CI cannot verify WSL GPU behavior.

## Build the WSL distribution package

`scripts/build-wsl.sh dist/bilskirnir.wsl` builds `wsl/Dockerfile` (Ubuntu 24.04, Docker Engine, Compose, Buildx, the NVIDIA Container Toolkit and the installation files), exports the container filesystem and compresses it. Test a package with `wsl --install --from-file dist\bilskirnir.wsl --name Bilskirnir-test`, run the first-start setup, then `wsl --unregister Bilskirnir-test`. Release tags attach the package to the GitHub release. Keep the files under `wsl/` in sync with `compose.ghcr.yml` and `.env.example`, which the Dockerfile copies.

The package pins `MANAGER_IMAGE` to the version in `Cargo.toml`, or to `BILSKIRNIR_VERSION` when it is set, so a package built before its tag is published cannot download its manager yet; set `BILSKIRNIR_VERSION` to a published release to test a first start that downloads. The `checks` job refuses a `v*` tag that differs from the version in `Cargo.toml`, and the package job waits until all three images of the tag are published.

The manager image bundles `wsl/bilskirnir` under `/app/install`, and `bilskirnir update` installs it from a newer release, so a change to the command reaches installed distributions with the next release. The command already installed decides from two lines of the new one, `CLI_VERSION=`, which the package build and the update fill in, and `NEEDS_PACKAGE=`, so both keep their form. `wsl/Dockerfile` records the level of the package's own files in `/usr/lib/wsl/package-level`. When the command starts relying on a package file that older packages lack or have in another form, raise that level and `NEEDS_PACKAGE` together; installations from older packages then keep their command until they install a newer package, so prefer a command that copes with the older files.

## Keep older installations working

The ownership labels (`bilskirnir.*`), the `bilskirnir-*` resource names, the `bilskirnir_session` cookie and the `X-Bilskirnir-Request` header are identifiers that existing containers, images, volumes and sign-ins depend on. Changing them requires a migration, not a naming edit.

Preserve user containers, images and volumes during development. Never use daemon-wide pruning as a test cleanup step. See [installation and recovery](INSTALLATION.md) for the data that must survive an upgrade.
